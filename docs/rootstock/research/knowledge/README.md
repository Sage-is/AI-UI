# knowledge survey: files, extraction, chunks, vectors and retrieval

Pinned: aa25d9b + pending 3.2.1 paths

Read on 2026-10-23, read-only; nothing was run. Backend paths are relative to `app/backend/sage_is_ai/`; all others start at the repo root. "Read, not run" marks a claim proven by reading code only. `plan:N` is line N of the approved Rootstock plan. The Phase 0 probe ran in the shipped image and is quoted from its result file.

An upload runs extraction, chunking and embedding inside the request, on the event loop. The extracted text lands on the file row. Chunks and vectors go to Chroma, once under `file-<id>` and again under the knowledge base id. At chat time the browser sends file and collection ids back, and the server searches them without asking who may read them. On the production box the vector store was empty, and every layer swallowed the error.

## 2. What really runs

- **Step 1, upload.** `POST /api/v1/files/` (`routers/files.py:85-231`) reads the whole file into memory and writes `<uuid>_<name>` to the uploads directory (`routers/files.py:137`; `storage/provider.py:40-50`). An extension allow-list applies unless the call is `internal` (114-125). The size and count limits are never checked on the server: the browser reads them from `/api/config` (`main.py:2002-2003`; `app/src/lib/components/chat/MessageInput.svelte:662-671`). The storage tags carry the uploader's email, id and name (131-137), which local storage ignores. `Files.insert_new_file` writes the row (139-154).
- **Step 2, processing happens inside the request.** With `process=true`, the default, the handler awaits `process_file` (155-205). Audio and webm go to speech-to-text first (157-178). Images and video are skipped unless the engine is `external` (179-191). An unknown content type is processed anyway (192-205). A failure does not fail the upload; it comes back as an `error` field on the row (208-216).
- **Step 3, `process_file` has three modes** (`routers/retrieval.py:1430-1672`). (a) The caller supplies `content`, used for audio and for "update content": it drops `file-<id>` and rebuilds it (1444-1470). (b) The caller names a `collection_name`, used when a file joins a knowledge base: it re-reads the chunks of `file-<id>`, or falls back to `file.data.content` (1471-1501). (c) Otherwise it loads the stored original through `Loader` (1502-1566). `ingestion_mode == "ai_parsed"` then rewrites the text with a model call (1568-1604). The text and its sha256 are stored (1606-1613) and, unless embedding is bypassed, embedded (1615-1652).
- **The event loop does the work.** `process_file` is `async def` (1431) and calls the blocking `loader.load` (1536) and `save_docs_to_vector_db` (1617) directly, the latter with `requests` calls to the embedding endpoint (`retrieval/utils.py:821-839`). `run_in_threadpool` appears only in the wizard (`routers/retrieval.py:584,618,664`). The server runs one worker (`app/backend/start.sh:276`), so a large upload, or `POST /reindex`, which awaits `process_file` once per file (`routers/knowledge.py:239-245`), stalls every other request until it ends (read, not run).
- **Step 4, loaders.** `Loader._get_loader` (`retrieval/loaders/main.py:278-459`) picks by engine: `external`, `tika`, `datalab_marker`, `docling`, `document_intelligence` (Azure) and `mistral_ocr`. The default branch picks by extension: PyPDF for pdf, CSV, BSHTML for html, TextLoader for md, txt and source files, Docx2txt for docx, and `Unstructured*` loaders for xls, xlsx, ppt, pptx, rst, xml, epub and odt. Anything else is read as text with a detected encoding (454-457). The built-in loaders live in the `rag-loaders` overlay (`retrieval/loaders/main.py:8-64`). The census engine is empty, so the built-in set runs.
- **Step 5, chunk, embed, insert.** `save_docs_to_vector_db` (`routers/retrieval.py:1205-1418`) refuses a chunk set whose `hash` metadata already exists in the collection (1236-1246). It splits by `TEXT_SPLITTER`: character (the default), token or markdown header (1248-1317), with 1,000 characters and 100 overlap by default (`config.py:2556-2563`). Every chunk gains an `embedding_config` of engine and model (1322-1335). A collection that already exists, with neither `overwrite` nor `add`, is silently kept (1349-1361). Texts are embedded in one call with newlines turned into spaces (1394-1398), and each row gets a fresh uuid (1400-1413).
- **Step 6, a file joins a knowledge base.** `POST /{id}/file/add` (`routers/knowledge.py:357-439`) needs a truthy `file.data` (388-392), runs `process_file(collection_name=<kb id>)` (396-400) and appends the id to `knowledge.data.file_ids` (409-416). Chunks now exist twice, under `file-<id>` and under the KB id. Mode (b) reads the file's chunks, and `save_docs_to_vector_db` embeds those same texts a second time (1394-1398). `knowledge.data` is `None` until the first file arrives (`models/knowledge.py:94-98`).
- **Step 7, removal.** Removing a file from a KB deletes the KB's chunks by `file_id`, the `file-<id>` collection and the file row, and never calls `Storage`, so the original stays on disk (`routers/knowledge.py:514-599`, row deleted at 566). Deleting a KB deletes its collection and clears the agent references, and leaves its files, their `file-<id>` collections and the originals (607-663). Deleting a file deletes the row and the original, then calls `delete` on `file-<id>` with no ids and no filter, which the Chroma driver ignores (`routers/files.py:609-645`; edge case 6).
- **Step 8, chat-time retrieval.** `chat_completion_files_handler` (`utils/middleware.py:1029-1105`) asks a model for queries (1037-1062), then calls `get_sources_from_items` in a thread (`retrieval/utils.py:531-754`) for every `files` item the browser sent: `text`, `note`, `file`, `collection`, `docs`, `collection_name` or `collection_names`. Full-context mode reads stored text (590-628, 636-668). Vector mode searches `file-<id>`, the KB id or a named collection (629-687). `query_collection` embeds all queries in one call, searches each collection in a thread pool, drops duplicates by the sha256 of the text and keeps the top `k` (309-358, 252-289), default 3 (`config.py:2367-2369`). The score is `(2 - d) / 2` on cosine distance (`retrieval/vector/dbs/chroma.py:83-87`). The relevance threshold `r` and the reranker act only in hybrid mode.
- **Step 9, hybrid search, off.** `rag.enable_hybrid_search` is false in both census databases and by default (`config.py:2386-2390`). Turned on, it fetches the whole collection, builds a `BM25Retriever` for every query, ensembles it with the vector search and reranks through the grafted `bge-reranker` (`retrieval/utils.py:150-228,361-434,1035-1084`). It needs the `rag-loaders` overlay for langchain (26-47). With hybrid off, no reranker is ever called, because `get_sources_from_items` hands the reranker only to the hybrid functions (704-713).
- **Step 10, the vector DB abstraction.** `VectorDBBase` declares nine methods (`retrieval/vector/main.py:23-86`). `factory.py` builds one of six types (`retrieval/vector/type.py:4-10`): milvus, qdrant (two drivers, single and multitenancy), chroma, pinecone, elasticsearch, opensearch. Drivers by size: chroma 196, qdrant 246, opensearch 266, elasticsearch 299, qdrant multitenancy 348, milvus 413, pinecone 581. Only chroma is ever delivered: as the `vector-chroma` overlay (`sprigs/supervisor.py:380-412`) or, failing that, a pinned `uv` install of `chromadb==0.6.3` at runtime (`sprigs/vector_bootstrap.py:47,100-144`). The other five install through the wizard (`app/backend/requirements.txt:78-79`), have no gate, and one driver says "only tested halfwat" (`retrieval/vector/dbs/elasticsearch.py:179`). A failed import leaves `VECTOR_DB_CLIENT` as None (`retrieval/vector/factory.py:50-60`).
- **Step 11, embedding dispatch to Sprigs.** `get_embedding_function` (`retrieval/utils.py:437-517`) knows five engines: `""` local sentence-transformers, `chroma` bundled ONNX, `ollama`, `openai` and `azure_openai`. Grafting an embedding Sprig sets engine `openai`, the model, the loopback URL and the key `sprig-local`, then rebuilds the function (`sprigs/embedding_dispatch.py:24-63`); the sentinel key marks the saved config as Sprig-owned (21). The reranker, Tika and Docling dispatchers do the same for their slots (`sprigs/reranker_dispatch.py:24-54`; `sprigs/tika_dispatch.py:20-34`; `sprigs/docling_dispatch.py:19-31`). `ensure_embedding` grafts the cultivar whose `model` matches the saved one, or falls back to a multi-gigabyte runtime install (`sprigs/embedding_bootstrap.py:39-99`; `routers/retrieval.py:559-609`).
- **Step 12, where the text lives, and re-index.** `process_file` writes `file.data.content` and `file.hash` (`routers/retrieval.py:1606-1613`). Mode (b) falls back to that text when `file-<id>` is missing (1488-1499), and `process_files_batch` reads only the stored text (2052). So a re-index needs no original for any row that has `data.content`: 1,080 of 2,193 file rows (49%) in the July snapshot, and the same 1,080 in the September backup. `POST /reindex` (`routers/knowledge.py:192-268`) deletes each KB collection and calls `process_file` once per file, in the request.
- **Step 13, the import-cache trap.** Sprig tars carry a fixed mtime, so extracting an overlay leaves the directory mtime unchanged and Python's `FileFinder` keeps its stale listing (`routers/retrieval.py:40-52`). Seven sites call `importlib.invalidate_caches()` to cope: `routers/retrieval.py:52`, `retrieval/utils.py:34`, `retrieval/loaders/main.py:39`, `retrieval/web/utils.py:56`, `sprigs/vector_bootstrap.py:85`, `sprigs/supervisor.py:1184` and `utils/pdf_generator.py:30`. Each guards a lazy import of an overlay package, and a missing one answers 503 "graft the rag-loaders Sprig" (`routers/retrieval.py:59-66`).
- **Step 14, the production incident.** The card at `TODO.md:148-156` records that all 13 knowledge bases with files answered queries with 200 and no hits, and adding a file answered 400. `vector_db_ready` was false, `vector-chroma` was not grafted, so `VECTOR_DB_CLIENT` was None (`'NoneType' object has no attribute 'search'` ×26). `query_collection` swallowed those errors. `chroma.sqlite3` held 0 collections against 19 knowledge bases, with 654 orphaned HNSW directories, the same count as in July. The embedder was `mock-embedding`, sha256-seeded noise that re-roots on every boot and that diagnostics reports as `ok`. The planned fix is to graft `vector-chroma` and a real 384-wide cultivar, prune the mock, and call `POST /reindex`.
- **Step 15, the Phase 0 probe.** In the shipped image (Python 3.11.17, SQLite 3.54.0) `enable_load_extension`, FTS5, JSON, R-tree and the math functions all work (`scripts/rootstock/sqlite_probe.py`; its output is `sqlite-probe-result.txt` beside this note). sqlite-vec 0.1.9 scalar `vec_distance_cosine` over 50,000 × 384 float32 BLOBs took 45, 39 and 40 ms in three runs, about 40 ms. Pure-Python cosine on pre-normalised vectors took 52 ms at 5,000 and 204 ms at 20,000. The data were random unit vectors in an in-memory database, 76.8 MB at 50,000 rows. The plan keeps both stores: SQLite in the same file by default, and the `vector-chroma` Sprig opt-in for big corpora (plan:132-134).

## 3. Edge cases worth keeping

Marks: **K** carry over, **F** fix on the way, **D** dies with a cut feature.

1. **(F) Retrieval does not check who may read.** `get_sources_from_items` searches `file-<id>`, a KB id or any named collection taken from the request body, and checks access only in full-context mode, with `has_access`, which the owner of a private KB fails too (`retrieval/utils.py:590-687`; `utils/middleware.py:1278`; `main.py:1762`; `utils/access_control.py:137-153`). `POST /query/doc` and `/query/collection` take any collection name from any verified user (`routers/retrieval.py:1815-1943`). Why: a user who learns an id reads that data (read, not run). The Rootstock's `knowledge_search` must filter by what the caller may see.
2. **(F) A file joins any KB by id, and file access runs through one KB.** The add route checks the KB's write access and not the file's owner (`routers/knowledge.py:382-392`). `has_access_to_file` decides through `file.meta.collection_name` (`routers/files.py:53-77`), which every `process_file` call overwrites with its last collection (`routers/retrieval.py:1631-1636`). Only 392 of 2,193 files carry the key. Why: who may read a file depends on whichever KB embedded it last, and 82% of rows never had a key.
3. **(F) `POST /reindex` deletes empty knowledge bases.** A KB whose `data` is not a dict is deleted (`routers/knowledge.py:209-220`), and a new KB starts with `data = None` (`models/knowledge.py:94-98`). In both census databases 13 of 18 hold a dict, so 5 would go. The board's remedy names this route (`TODO.md:156`). Why: the plan's re-index job must rebuild chunks and never delete a knowledge base.
4. **(F) Updating a KB writes the whole form.** `update_knowledge_by_id` sets every field the form holds, so an API caller that omits `data` clears `file_ids` while the chunks stay (`models/knowledge.py:164-176`; `routers/knowledge.py:309-345`) (read, not run). The SPA sends `data` back unchanged, which can overwrite a concurrent add with stale ids (`app/src/lib/components/workshop/Knowledge/KnowledgeBase.svelte:459-463`). Why: both drop files from a KB with no error.
5. **(F) A GET writes, and lists cost N+1 queries.** `get_knowledge` and `get_knowledge_list` prune missing file ids and save them (`routers/knowledge.py:73-91,130-148`). `get_knowledge_bases` loads every KB and looks up each owner (`models/knowledge.py:128-143`), then the route queries files per KB. Board card `TODO.md:970`. Why: a read storm can write.
6. **(F) Deletes leave debris.** Removing a file from a KB drops the row and not the original (`routers/knowledge.py:566`). Deleting a KB leaves its files and their `file-<id>` collections (607-663). Deleting a file calls `delete` with neither ids nor a filter, which the Chroma driver treats as nothing to do, so `file-<id>` survives (`routers/files.py:628`; `retrieval/vector/dbs/chroma.py:173-190`) (read, not run). Why: orphans pile up in storage and in vectors; the production box holds 654 orphaned HNSW directories (`TODO.md:151`). The plan deletes chunks in the same transaction as the row.
7. **(F) The limits live in the browser.** The upload route has no size or count cap and reads the whole file into memory (`routers/files.py:85-231`; `storage/provider.py:43-44`). `rag.file.max_size` and `max_count` are unset in both census databases. Why: any API caller can upload any size.
8. **(F) Processing blocks the event loop.** `process_file`, `loader.load` and the embedding calls are synchronous work inside `async def` handlers (`routers/retrieval.py:1431,1536,1617`), and `POST /reindex` awaits them file by file (`routers/knowledge.py:239-245`). One uvicorn worker serves everything (`app/backend/start.sh:276`). Why: chat events and Space replies stall while a document is embedded (read, not run), and Cloudflare cuts the request at 100 s (`TODO.md:156`).
9. **(K) Stored text is the rebuild source, for 49% of rows.** `file.data.content` and `file.hash` exist on 1,080 of 2,193 rows, the same 1,080 in both databases. A file can join a KB only when `file.data` is truthy (`routers/knowledge.py:388-392`), so KB files normally carry text (inferred; the census does not join knowledge to files). The other 1,113 rows hold no text: image attachments the extractor skips, or uploads whose processing failed. The census cannot split them (unverified). Why: a rebuild skips those rows and must say so.
10. **(F) Every layer swallows errors.** The Chroma driver answers None on any exception in `search`, `query` and `delete` (`retrieval/vector/dbs/chroma.py:98-99,121-122,187-192`). `query_collection` and `get_sources_from_items` log and go on (`retrieval/utils.py:329-331,355-358,727-728`). The `Files.update_*` methods swallow (`models/files.py:182-211`). `save_docs_to_vector_db` returns True for an existing collection (`routers/retrieval.py:1357-1361`). Why: the incident passed every layer as a 200 with no hits.
11. **(K) A repeated chunk set is refused.** `hash` metadata already in the collection raises `DUPLICATE_CONTENT` (`routers/retrieval.py:1236-1246`), and the hash covers the whole text (1612). Adding the same file twice to a KB answers 400, and a changed file goes through `/file/update`, which deletes by `file_id` and re-adds (`routers/knowledge.py:442-506`). Why: keep the hash check, and answer a repeated add with a clear "already there" status.
12. **(K) The embedding model is recorded and never checked.** `embedding_config` rides on each chunk (`routers/retrieval.py:1327-1332`). `POST /embedding/update` swaps engine and model at once and leaves old vectors in place (311-417). A width mismatch raises inside Chroma, and `search` hides it. Why: the plan's "search refuses until re-indexed" (plan:134) needs the model on every chunk row.
13. **(K) The source shape is the UI contract.** A source is `{source, document[], metadata[], distances[]}` (`retrieval/utils.py:737-754`), stored on 1,678 of 9,216 assistant messages in July. The citation view reads `distances` as values in [-1, 1] (`app/src/lib/components/chat/Messages/Citations.svelte:22-42`), which `(2 - d) / 2` satisfies. Why: old chats and the Svelte chat read it.
14. **(K) The context block has a fixed form.** `<source id="n" name="...">` wraps each chunk (`utils/middleware.py:1371-1375`). The RAG template fills `[context]`, `{{CONTEXT}}`, `[query]` and `{{QUERY}}` (`utils/task.py:165-202`). An injected `<context>` tag only gets a log line (176-181). Why: keep the form; the injection check is weak.
15. **(F) Unknown file types are decoded as text.** Any extension the loader table does not name goes to `TextLoader` with a detected encoding (`retrieval/loaders/main.py:454-457`). Why: a binary upload becomes garbage chunks instead of an error.
16. **(F) The E5 prefixes are unset.** `RAG_EMBEDDING_QUERY_PREFIX` and `RAG_EMBEDDING_CONTENT_PREFIX` default to None (`config.py:2496-2498`), while the grafted wide cultivars are multilingual-e5-large, which is trained on a `query:` prefix for queries and a `passage:` prefix for documents. Whether the llama-server template adds them is (unverified). Why: it changes retrieval quality, and the answer belongs next to the model name in the Rootstock.
17. **(F) The mock embedder is a live engine.** `mock-embedding` serves sha256-seeded 384-wide noise, re-roots on every boot and reads as healthy (`sprigs/mock_embedding_server.py`, 93 lines; `TODO.md:152`). Why: the plan refuses it (plan:134), and the check must live in the store, not in diagnostics.
18. **(F) Embedding calls leave the box unfiltered.** `generate_openai_batch_embeddings` posts every chunk to the configured URL (`retrieval/utils.py:805-852`), and the privacy filter never sees embeddings (`docs/federation.md:91`). Why: with a hosted embedding URL, document text leaves as it is; the Rootstock's `embed` should refuse an external connection unless the operator opts in.
19. **(F) File lists carry the text.** `GET /api/v1/files/` returns every row with `data.content` unless `?content=false` (`routers/files.py:239-251`). Why: one call returns every extracted document the caller owns, or all of them for an admin.
20. **(D) Attaching a web page is broken.** `process_web` reads `WEB_SEARCH_CONCURRENT_REQUESTS` and `BYPASS_WEB_SEARCH_EMBEDDING_AND_RETRIEVAL`, which no config defines, so it should answer 400 (`routers/retrieval.py:1770,1777`) (read, not run), yet the chat calls it (`app/src/lib/components/chat/Chat.svelte:677`). `processWebSearch` posts to a route that does not exist (`app/src/lib/apis/retrieval/index.ts:140-148`). `retrieval/web/utils.py` (694 lines) is reachable only through this route.
21. **(D) Two admin routes cannot work.** The hybrid branch of `query/doc` reads `form_data.hybrid_bm25_weight`, which its form lacks, and passes `user` to a function that takes none (`routers/retrieval.py:1853-1858`; `retrieval/utils.py:150-160`). `POST /delete` passes `metadata=` to `delete`, which has no such argument, and hides the error (`routers/retrieval.py:1967-1976`; `retrieval/vector/main.py:74-80`).
22. **(K) A temporary chat embeds nothing.** `text` items carry their content inline (`retrieval/utils.py:556-577`), and `rag.bypass_embedding_and_retrieval` is false in both census databases. Why: private chats stay out of the vector store.

## 5. Rootstock equivalent

- **Modules, `knowledge/` (plan cap 1,300).** `files.py` (upload, delete), `extract.py`, `index.py` (chunk, embed, write), `search.py` and `stores/{sqlite,chroma}.py`. Each store exports `index`, `search`, `delete` and `count`; a missing function means unsupported (plan:134). Ops: `file_upload`, `file_get`, `file_delete`, `knowledge_create`, `knowledge_get`, `knowledge_list`, `knowledge_update`, `knowledge_delete`, `knowledge_add_file`, `knowledge_remove_file`, `knowledge_search` and `knowledge_reindex`. Together they replace 40 routes and about 11,060 lines of Python.
- **Upload is a job, not a request.** The upload route stores the original and answers at once. A background job extracts, chunks and embeds, and a side table `rs_file_state(file_id, status, error, model, chunks)` carries `queued`, `extracting`, `embedding`, `ready` or `failed`, because the `file` table belongs to Alembic until its hand-off. Size and count caps are enforced on the server (edge case 7). Nothing runs on the event loop.
- **Extraction.** The core reads text, markdown, csv, html and source files with the standard library, and rejects other types instead of decoding them (edge case 15). PDF and Office files go to a service Sprig over loopback (Tika and Docling exist, `sprigs/supervisor.py:515,551`) or to `pypdf` if the Rootstock carries it. The census records no content-type split, so how much must be in core is open (unverified). With the cloud engines gone, no original leaves the box.
- **Chunker.** A recursive character splitter of about 50 lines with 1,000 characters and 100 overlap, as `config.py:2556-2563` defaults. Today the base image cannot chunk at all without the `rag-loaders` overlay (`routers/retrieval.py:59-66`), so the splitter belongs in the core, not in a Sprig.
- **Embedding.** `embed` goes through the `openai` kind to the loopback Sprig, with the model recorded on every chunk and the prefix pair stored beside the model name (edge case 16). It refuses `mock-embedding` (plan:134) and, by default, any external connection (edge case 18). Each call writes a receipt.
- **The SQLite store.** One table in the main database file, `rs_knowledge_chunk(knowledge_id, file_id, ord, text, meta, model, embedding BLOB float32)` (plan:134), with an FTS5 mirror for hybrid search. Chunks go in and out in the same transaction as their rows, and vectors never sit in an attached second file. The probe supports the plan: extension loading, FTS5, JSON and math all work, and sqlite-vec scores 50,000 × 384 vectors in about 40 ms. Two limits come with it. The probe used 384 wide vectors and an in-memory database, while the grafted wide cultivars are 1,024 wide, 2.7 times the bytes per row. A linear extrapolation gives about 110 ms at 50,000 rows and about 540 ms for the pure-Python fallback at 20,000 (unverified). So cap the fallback in `rows × width`, about 7.7 million, not in rows. The wheel must ship in the image, since the probe installed `sqlite-vec` at run time and the plan removes `uv`.
- **One embedding per file, or one per knowledge base.** The plan keys chunks by `knowledge_id` and `file_id`, which keeps today's double write: a file in two knowledge bases is embedded twice (Step 6). Keying chunks by `file_id` and reading membership from `knowledge.data.file_ids`, which 13 of 18 rows hold, embeds once, makes search `WHERE file_id IN (...)`, and lets a file delete remove its chunks in one transaction. A Chroma-backed KB would still index its own copy. Decide before F5.
- **Search.** `knowledge_search(caller, query, knowledge_ids, limit)` (plan:85) first reduces `knowledge_ids` to those the caller may read, using the `access_control` lists with `None` meaning public (3 of 18 rows, inferred from the 15 dicts) and the owner always allowed (edge cases 1 and 2). It embeds the query once, scores `(1 + cos) / 2` so the citation view keeps its range (edge case 13), drops duplicates by text hash, applies the relevance floor in every mode (today only hybrid does) and returns `{source, document[], metadata[], distances[]}`. Hybrid adds FTS5 rank fusion. A reranker Sprig, if grafted, scores the fused list in both modes. A store error is raised, never turned into zero hits (edge case 10).
- **Legacy item shapes.** `model.meta.knowledge` rows come in three forms (`utils/middleware.py:1201-1221`): `{id, type: "collection"}`, `{collection_name}` and `{collection_names}` marked `legacy`. Nine `model` rows carry `meta.knowledge`; the census does not show which forms they use (unverified), so the Rootstock reads all three.
- **Re-index, a job that never deletes a knowledge base.** For each KB and each file: take `file.data.content` (or extract the original when there is no text), re-chunk, re-embed with the current model, and swap the file's rows in one transaction. It reports the files it skipped for lack of text, refuses to start while the embedder is the mock, and records progress in `jobs/`. After an embedding model change `knowledge_search` refuses until the job ends (plan:134); the model on every chunk row is what makes that check possible.
- **The Chroma opt-in runs as a service Sprig.** The existing driver already speaks `chromadb.HttpClient` (`retrieval/vector/dbs/chroma.py:44-52`), so `vector-chroma` becomes a loopback process, not a site-packages overlay. That removes the `invalidate_caches` sites (Step 13), the restart-to-activate rule and the `uv` fallback, and it keeps the ONNX embedders off the overlay (`sprigs/supervisor.py:302-303`). The production store holds 0 collections (`TODO.md:151`), so there is nothing to migrate. For any box with live Chroma data, rebuild from the stored text and do not copy vectors.
- **Diagnostics.** The doctor reports the embedder and whether it is the mock, chunk rows against file rows, files with text and no chunks, chunks whose file is gone, chunks whose model differs from the saved one, and for a Chroma KB the collection count against `rs_` rows. "Unknown" never reads as "ok". This replaces `vector_db_ready`, which was false while every gate stayed green.
- **Deletes.** A file delete removes the row, the original and its chunks together. A KB delete removes its membership and, for a Chroma KB, its collection; the files stay (edge case 6 shows today's gaps).
- **Plan check, schema.** `rs_knowledge_chunk` repeats the double embedding (see the file-keyed option above). The plan's "re-index from `file.data.content`" (plan:134) holds for 1,080 of 2,193 rows only. The plan's `routers/retrieval.py:1607` for the stored text is right (1606-1613), but its incident cite `TODO.md:141` is now `TODO.md:151` and the card spans `TODO.md:148-156`.
- **Plan check, reranker.** The plan lists the `bge-reranker` GGUF Sprig among the Sprigs it relies on (plan:134). Today the reranker is reachable only through hybrid search, which both census databases store as off. The Rootstock needs a stated reranking step, or the Sprig is dead weight.
