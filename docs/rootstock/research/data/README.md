# data survey: the schema the Rootstock will meet

Pinned: aa25d9b + pending 3.2.1 paths

The Rootstock reads the same SQLite file the old app writes, `DATA_DIR/webui.db`, through unmanaged Django models. This note records what is in that file: tables, declared types against stored types, who writes each table, and the JSON shapes. Backend paths start `app/backend/sage_is_ai/`. Types come from the snapshot DDL (`sqlite_master` of the 2026-07-12 file, schema only, opened `mode=ro&immutable=1`), from the census, and from direct read-only counts on the same file: the digit length of time columns (declared against stored, item 3), the literal text `null` (item 6), the `shared-` clone rows (edge case 4) rows that name no user (edge case 7), the stored path prefix (edge case 14) and the JSON types inside `chat.chat` (shapes). Units and writers come from the code.

## 1. Surface

**Tables.** A 3.1.0-era snapshot holds 28 tables: 27 application tables plus `alembic_version`. Today's tree adds `privacy_map` and `privacy_audit` (revision `c2d3e4f5a6b7`), so an upgraded file holds 29 application tables plus `alembic_version`.

- 24 tables have an ORM class: 23 in `models/` (383 of its 5,993 lines) and `Config` at `config.py:70`. Twenty-two are in the snapshots.
- 5 tables are orphans that no application code reads or writes: `channel_member`, `chatidtag`, `document`, `migratehistory`, `tool`. Only migrations touch them, and `internal/legacy_db.py` reads `migratehistory`.
- Alembic head on this tree is `c2d3e4f5a6b7` (20 revisions in `migrations/versions/`, 1,376 lines, linear, one head). Both snapshots stand at `b1c2d3e4f5a6`, one revision behind.
- The frozen peewee schema is `internal/legacy_schema.sql`: 14 tables and 17 unique indexes, 39 lines. `internal/legacy_db.py` replays it on a fresh file (132 lines).
- The snapshots hold 230 columns and 32 indexes, all unique. Today's tree adds 10 columns. The file declares no foreign key, trigger or view.
- Declared types in the snapshots: TEXT 102, JSON 39, INTEGER 27, BIGINT 26, VARCHAR(255) 25, BOOLEAN 5, DATETIME 5, VARCHAR(32) 1.
- File facts (2026-07-12): 170,254,336 bytes, 41,566 pages of 4,096, journal `delete`, 338 free pages, `user_version` 0. Second snapshot (2026-09-27): 178,032,640 bytes, 18 free pages.
- Clients of the file: 21 of the 31 modules in `routers/`, 9 `pages/*_panel.py` modules, `socket/main.py`, `bridges/`, `utils/` and `main.py`. They reach the tables through 22 singletons (`Chats`, `Users`, and so on) and reach `config` through `config.py`.

**Declared against stored.** Nine facts the models must not guess. Counts are from the census unless a line says otherwise.

1. **Integer times under DATETIME.** `chat.created_at` and `chat.updated_at` are declared DATETIME and hold integer seconds in all 1,982 rows (2,124 in the second snapshot). The ORM says BigInteger (`models/chats.py:31-32`). Django's `DateTimeField` would fail to parse them.
2. **Text times under DATETIME.** `config.created_at`, `config.updated_at` (1 row) and `migratehistory.migrated_at` (19 rows) hold text. `created_at` is SQLite `CURRENT_TIMESTAMP`, UTC. `updated_at` is `datetime.now()` in the container's zone (`config.py:93`). `legacy_db` writes `migrated_at` as UTC ISO text with a space (`internal/legacy_db.py:71`).
3. **Three time units.** Fifteen tables store seconds. Six store nanoseconds: `message`, `message_reaction`, `channel`, `note`, `bridge_connection`, `bridge_thread` (`models/messages.py:101,207,222`, `models/spaces.py:79-80`, `models/notes.py:85-86`, `models/bridges.py:179-180,289-290`). A nanosecond value has 19 digits and passes 2^53, so JavaScript cannot hold it exactly. Inside `chat.chat` the chat `timestamp` is milliseconds (`app/src/lib/components/chat/Chat.svelte:2000`) and a message `timestamp` is seconds (`:1462`). A digit count on the 2026-07-12 file agrees with the code: 19 digits in every `message`, `channel` and `note` row; 10 digits in `chat`, `user`, `file`, `model`, `feedback`, `knowledge`, `folder`, `group`, `prompt`, `tool` and `function`.
4. **Booleans are integers.** The five BOOLEAN columns and the INTEGER flags `auth.active`, `chat.archived`, `function.is_active`, `function.is_global` hold 0 or 1. `chat.pinned` is nullable: 78 NULL, 1,889 zero, 15 one. `model.is_active` is 330 on, 2 off.
5. **JSON hides in TEXT.** 39 columns are declared JSON. Six live columns declared TEXT also hold JSON: `user.settings`, `user.info`, `model.meta`, `model.params`, `function.meta`, `function.valves`. The orphan `tool` adds three more. `JSONField` is a `TypeDecorator` over Text (`internal/db.py:21-40`); the other columns use SQLAlchemy `JSON`. Both write `json.dumps` output.
6. **Three encodings of "no value".** A JSON column can hold SQL NULL, the text `null`, or a value. `JSONField.process_bind_param` returns `json.dumps(None)` for None (`internal/db.py:25-26`), so unset `user.settings` and `user.info` read back as the four characters `null`. All 32 `user.info` values are the text `null`, as are 13 of 32 `user.settings`. `model.access_control` is 185 NULL, 107 text `null`, 2 `{}` and 38 objects. `file.access_control` is 42 NULL and 2,151 text `null`. `knowledge.access_control` has 3 text `null` beside 15 objects; `note.access_control` 2 beside 9 `{}` and 6 objects; `prompt.access_control` 1 beside 7 `{}`. `tag.meta` is `null` in all 1,395 rows, `knowledge.data` in 5 of 18, `group.meta`, `channel.meta` and `folder.items` in every row. Those counts come from a direct read-only count of the literal text on the 2026-07-12 file, not from the census. Django's `isnull=True` matches SQL NULL only.
7. **`access_control` is a protocol.** `None` means public to read, `{}` means owner only, and `{"read": {...}, "write": {...}}` with `group_ids` and `user_ids` names the rest (`models/models.py:79-94`, `utils/access_control.py:137-153`). In the snapshots `prompt.access_control` is seven `{}` and one non-dict; `note.access_control` is 15 dicts, 9 of them `{}`.
8. **`id` is not a key.** Ten tables have no PRIMARY KEY at all, only a UNIQUE index on `id`: `auth`, `chat`, `chat_share`, `chatidtag`, `file`, `function`, `memory`, `model`, `tool`, `user`. Peewee built them (`internal/legacy_schema.sql:12-38`) and Alembic's `create_table` calls skip tables that exist (`migrations/versions/7e5b5dc7342b_init.py:29-37`). The ORM declares `id` as the primary key, so SQLAlchemy never notices. Two more keys differ from the ORM: `prompt` and `folder` (edge cases 2 and 3).
9. **Affinity explains the mismatches.** SQLite gives NUMERIC affinity to any declared type it does not recognise as integer, text, blob or real, which includes DATETIME, BOOLEAN and JSON (SQLite's datatype rules, not read in this repo). An integer sits quietly in a DATETIME column, and a JSON column handed the bare text `5` would return the integer 5. No snapshot JSON column holds an integer (the census shows only text and NULL), so nothing is damaged today.

## 2. What really runs

**Opening the file.** Import order fixes the schema before the first request.

1. `env.py:312-319`: an `ollama.db` in `DATA_DIR` is renamed `webui.db`; `DATABASE_URL` defaults to `sqlite:///{DATA_DIR}/webui.db`.
2. `internal/db.py:43-52`: `create_engine(url, connect_args={"check_same_thread": False})`. No pragma, no `timeout`, so the driver's own 5 s busy timeout applies and the journal stays `delete`. Then `legacy_db.prepare(engine)` (`internal/legacy_db.py:122-132`): an empty file gets `legacy_schema.sql` and 19 `migratehistory` rows; a file with `migratehistory` gets `chat_share` if revision 019 is missing, or is refused if 001-018 are; a file with only `alembic_version` is left alone; legacy tables with no record are refused. `internal/test_legacy_db.py` pins each outcome.
3. `config.py:47-67`: `run_migrations()` runs `alembic upgrade head` at import, on its own `NullPool` connection (`migrations/env.py:65-72`). Autogenerate targets `Auth.metadata`, which is every model imported so far (`migrations/env.py:21`). There is no `include_object` filter.
4. `config.py:104-122`: a leftover `config.json` is saved into `config` and renamed `old_config.json`. `CONFIG_DATA` is read once into memory.
5. Every model method opens its own session with `get_db()` (`internal/db.py:61-69`), commits and closes. No transaction spans two model calls. The scoped `Session` serves only `main.py:1465` and `main.py:2292`.

Provider keys, SMTP and OAuth secrets sit in it as plain strings.
- **Smaller shapes.** `feedback.snapshot` is `{chat: <whole chat>}` in 30 of 30 rows, beside `data` (`rating`, `model_id`, `comment`, `reason`, `sibling_model_ids`, `tags`, `details`) and `meta` (`chat_id`, `message_id`, `message_index`, `model_id`, `base_models`). `folder.data` is `{files, system_prompt}` in 7 of 14 rows. `note.data` is `{content, files}` in 17 and 13 rows. `channel.data.agents` lists a Space's agents (`models/spaces.py:132-136`). A Space `message.data.agent` marks an agent post and `message.user_id` is then the sentinel `__agent__`, which is not a `user` row (`routers/spaces.py:43,49`).

## 3. Edge cases worth keeping

1. **Ten tables have no primary key.** They carry a UNIQUE index on `id` and nothing else (`internal/legacy_schema.sql:12-38`); Alembic skips tables that exist (`migrations/versions/7e5b5dc7342b_init.py:29`). A Django model with no `primary_key=True` field invents an `id` AutoField that collides with the real column. Set `primary_key=True` on `id` by hand.
2. **`prompt` is keyed by a column the ORM does not declare.** The file's key is integer `id`; the ORM names `command` (`models/prompts.py:20`; `internal/legacy_schema.sql:22-23`). `command` is UNIQUE across all users, so one person's `/summary` blocks everyone's (`routers/prompts.py:80,92`). Keep `id` as the key and `command` unique.
3. **`folder` and `tag` have composite keys (`id`, `user_id`).** The ORM declares `Folder.id` alone (`models/folders.py:25`). A tag id is a slug of its name (`models/tags.py:50`), so two users share ids and a lookup without `user_id` is wrong. Django 5.2 adds `CompositePrimaryKey` (unverified here).
4. **Link sharing writes a clone into `chat`.** The clone has `user_id = "shared-<chat id>"` and the original's `share_id` points at it (`models/chats.py:291-313`); delete removes it by that prefix (`:337-345`, `:887-896`), and a "snapshot" share reuses it (`models/chat_shares.py:154-158`). So `chat.user_id` is not always a `user.id`. A direct count on the 2026-07-12 file confirms the shape: 29 `chat` rows have a `user_id` starting `shared-`, the other 1,953 rows have 24 distinct owners (24 plus 29 is the census's 53), and all 29 `share_id` values point at an existing row.
5. **Time has four spellings** (section 1, items 1 to 3): seconds, nanoseconds, milliseconds inside `chat.chat`, and text in `config`. Never map one to `DateTimeField`; give each unit a helper.
6. **"No value" has three spellings** (section 1, item 6). Filtering `model.access_control__isnull=True` finds the 185 NULL rows and misses the 107 rows that hold text `null`; both mean public.
7. **Deleting a user leaves most of their rows.** `Auths.delete_auth_by_id` calls `Users.delete_user_by_id`, which removes group membership and chats and nothing else (`models/auths.py:193-207`, `models/users.py:375-392`). Files, models, knowledge, prompts, folders, notes, tags, feedback, memories, Space messages, bridges and magic links stay, and the file declares no foreign key to stop or clean it. The leftovers in the 2026-07-12 file are small, by a direct count: 4 of 332 `model`, 16 of 1,395 `tag` and 1 of 17 `note` rows name no existing user. Decide whether the Rootstock inherits these orphans or deletes them.
8. **Creating a user is two commits.** `insert_new_auth` stages the `auth` row, lets `Users.insert_new_user` commit the `user` row in a second session, then commits its own (`models/auths.py:98-128`). A failure between the two leaves a user with no credentials.
9. **`last_active_at` is written on every authenticated request**, including GETs: as a background task for sessions (`utils/auth.py:277`) and inline for API keys (`:303`). It is the busiest write in the file. Batch it (at most once a minute per user) or the Rootstock keeps one writer transaction per page view.
10. **Whole-JSON writes lose edits.** The SPA's `POST /api/v1/chats/{id}` replaces top-level keys (`routers/chats.py:446-447`) while a stream persists one message by reading and rewriting the whole `chat.chat`, at ten call sites of `persist_message` (`utils/middleware.py:700`, calls from `:1519` to `:2243`) and in the socket emitter (`socket/main.py:644-708`). A stale `history` from the SPA can overwrite a newer streamed answer. `update_chat_by_id` swallows every exception and returns None (`models/chats.py:182-183`). The plan's `updated_at` check answers this.
11. **`config` is one row with two selection rules and whole-blob writes.** Reads take the newest id (`config.py:118`); writes update `first()` (`config.py:87`). Every write replaces the whole JSON from the process-local `CONFIG_DATA` (`config.py:85-95`, `:198-208`), so a second process, or a script editing the row, is overwritten by the next save. With `UVICORN_WORKERS` above 1 each worker has its own copy, refreshed only through Redis (`config.py:241-262`).
12. **Boot rewrites `config`.** A saved Sprig-backed embedding makes import-time code reset four keys (`main.py:1200-1212`), and the supervisor re-points two to four more per capability (`sprigs/embedding_dispatch.py:37-40`), each a whole-blob write. The loopback port and the sentinel key `sprig-local` are stored in the file, so a restored backup carries a dead address until that guard runs.
13. **A read path writes `function`.** Loading a Function rewrites `open_webui` imports into the row (`utils/plugin.py:82,140`) and switches `is_active` off when the module fails to load (`:119`). The Rootstock's Functions Sprig must not write while reading.
14. **`file.path` is absolute and read back as stored.** Upload stores `{UPLOAD_DIR}/{id}_{name}` (`storage/provider.py:46`), `get_file` returns it unchanged (`:52-53`), and `delete_file` re-roots only the basename (`:57-58`). A data directory mounted at another path keeps its rows but loses reads of old files. All 2,193 snapshot rows have a path, and every one begins `/app/backend/data/uploads/` (a direct count).
15. **`feedback.snapshot` copies a whole chat** into every feedback row (30 of 30). Deleting the chat does not delete the copy, so a private chat can outlive its deletion here.
16. **Real values and secrets sit in plain text in the file.** `privacy_map.real` holds the real value beside its stand-in (`models/privacy.py:23`). `config.data` holds provider keys, SMTP and OAuth secrets. `bridge_connection.config` holds platform credentials with nothing in the code that encrypts them (`models/bridges.py:26`). `auth.password` is bcrypt. Every database download, backup and snapshot carries all of it (`routers/utils.py:132-150`).
17. **Column names lag the product.** The table is `channel` and the ORM class `Channel`, while the product says Space (`models/spaces.py:17`); `message.channel_id`, `bridge_connection.channel_id` and `bridge_thread.sage_channel_id` carry the old word (`models/messages.py:40`, `models/bridges.py:27,67`). The file is frozen, so Django needs `db_column`. `message` holds Space posts, never chat messages.
18. **Search and groups need SQLite JSON1.** `json_each` and `json_array_length` run in `models/chats.py:644,662,675,757,798` and `models/groups.py:132`; chat search raises `NotImplementedError` on any other dialect (`models/chats.py:686`). Django's `JSONField` needs JSON1 too, so the Rootstock inherits the dependency.
19. **The frozen header must stay true.** `legacy_db.prepare` records all 19 peewee names so a rollback to 3.2.0 finds no work (`internal/legacy_db.py:15`), and leaves a file that has `alembic_version` alone (`:127-128`). A Rootstock-created fresh file must pass the same two tests, or `prepare` refuses it as "tables with no migration record" (`:129-131`).

## 4. Ceremony to drop

- **The Pydantic mirror layer.** `models/*.py` is 5,993 lines: 383 for the 23 table classes, 684 for 97 Pydantic classes (`*Model`, `*Form`, `*Response`), 3,645 for 22 table-helper classes with 248 methods, and imports and spacing for the rest. The Rootstock's signatures replace the Pydantic classes. Each helper method opens its own session; Django querysets replace them, minus the behaviours in section 3.
- **The peewee layer is already gone in the pending 3.2.1 paths.** 19 migrations (1,428 lines at `aa25d9b`) and `internal/wrappers.py` (42) are deleted. `internal/legacy_db.py` (132), `legacy_schema.sql` (39) and `test_legacy_db.py` (116) replace them and stay until the old app is deleted.
- **The Alembic tree is frozen, not ported.** 20 revisions, 1,376 lines, plus `migrations/env.py` (81), `migrations/util.py` (15), `script.py.mako` (27) and `alembic.ini` (114). The Rootstock never adds a revision (plan rule); it only runs the existing ones until a baseline replaces them.
- **Five orphan tables.** `channel_member`, `chatidtag`, `document`, `migratehistory`, `tool` get no model. `document` and `chatidtag` were inputs to two old revisions, now spent.
- **Dead peewee methods** `JSONField.db_value` and `python_value`, never called (`internal/db.py:35-40`, 6 lines).
- **Non-SQLite code.** `DB_NOT_SQLITE` guards (`routers/utils.py:144,225`), the refusal in `internal/legacy_db.py:111-115`, the `NotImplementedError` in chat search (`models/chats.py:685-688`) and `postgresql_using=` arguments in revisions. The image ships no other driver.
- **Boot shims.** The `ollama.db` rename (`env.py:312-317`) and the `config.json` import (`config.py:104-108`): 11 lines no current install needs.
- **The per-request commit.** `commit_session_after_request` (`main.py:1461-1466`, 6 lines) commits a scoped session that only `/health/db` uses.
- **Zero-row tables with ORM classes.** `bridge_connection`, `bridge_thread`, `chat_share`, `magic_link`, `memory`, `message_reaction` are empty in both snapshots (with `channel_member`, `chatidtag`, `document`). The census decides which ones the carve-outs keep.

## 5. Rootstock equivalent

**Ownership.** The plan's rule holds: unmanaged models over today's tables, `rs_*` tables for anything new, Alembic frozen. The 24 ORM classes take 391 lines today, so the unmanaged set should land near 400 counted lines (scaled from that size, not measured).

**What `inspectdb` output must get right.** Django 5.2 is not installed on the research host, so the Django-side claims below are from its documented behaviour and are unverified until the first `inspectdb` run on a fresh upgraded file.

1. **Times are `BigIntegerField`.** `chat.created_at` and `chat.updated_at` come out as `DateTimeField` because they are declared DATETIME; they hold integer seconds. Name the nanosecond columns (section 1, item 3) so no code treats them as seconds. `config` times and `migratehistory.migrated_at` are text; leave them `CharField`.
2. **JSON is TEXT on disk.** Django's SQLite introspection finds `JSONField` through a `JSON_VALID` CHECK, and none of these 45 columns has one, so expect `TextField`. Map the 39 JSON-declared and the six TEXT-declared columns (section 1, item 5) to `JSONField` by hand. Reads of the text `null` give `None`. Writing `None` stores SQL NULL, which the legacy reader also returns as `None`.
3. **`isnull` is not "empty".** Give `access_control` a manager that matches both NULL and JSON null, and name it `public()`.
4. **The `group` table.** Django quotes `db_table = "group"`, but raw SQL and `.extra()` must quote it too. Do not name the class `Group` or `User` beside `contrib.auth`; the plan's router keeps auth tables out of the file, but class names and reverse accessors still clash.
5. **Ten tables need `primary_key=True` on `id`** (edge 1). `prompt` keeps integer `id` as key and `command` as `unique=True` (edge 2).
6. **Composite keys.** `folder` and `tag` are (`id`, `user_id`): use `CompositePrimaryKey` (new in 5.2) or key on SQLite's `rowid`. No Django foreign key can target either, so `rs_*` rows point at them by plain columns with `db_constraint=False`, as the plan says.
7. **Booleans.** `chat.pinned` needs `null=True`. `auth.active`, `chat.archived`, `function.is_active`, `function.is_global` are declared INTEGER, so `inspectdb` says `IntegerField`; make them `BooleanField`.
8. **`managed = False` on every model**, no migration that touches a legacy table, and `makemigrations --check` clean in the test suite. Django turns `PRAGMA foreign_keys` on for its connections; the file declares none, so nothing trips.
9. **A schema-drift test.** Build a fresh file the way production does (`legacy_db.prepare`, then Alembic) and compare `PRAGMA table_info` with the models' columns, so a new Alembic revision cannot drift unseen.
10. **Exclude the orphans and `alembic_version`** from the generated file.
11. **Write what the old validators accept.** The plan's rollback test needs the legacy app to read Rootstock rows. Its Pydantic types reject NULL where a value is required: `model.params` and `model.meta` must be objects (`models/models.py:102-117`), `group.description` a string and `group.user_ids` a list (`models/groups.py:41-56`), `knowledge.description` a string (`models/knowledge.py:59-74`), `chat.chat` an object (`models/chats.py:42-58`). A NULL in one of these makes the old reader raise: a lookup by id swallows the error and returns None (`models/models.py:207-213`), a list call fails outright (`:170-172`).
