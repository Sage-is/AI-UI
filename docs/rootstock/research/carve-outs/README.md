## 2. What really runs

**Bridges, inbound.** A platform event reaches `process_incoming` (`bridges/pipeline.py:36-71`) by two doors: `POST /api/v1/bridges/webhook/{id}`, where the adapter checks the signature and parses the body (`routers/bridges.py:91-148`), or an adapter's polling loop through `set_incoming_handler` (`bridges/manager.py:183`). The connection must exist and be enabled, and the sender must pass the allowlist. The sender becomes a Sage user (`:386-440`): `oauth_sub` `bridge:<platform>:<id>`, email `bridge_<platform>_<id>@bridge.local`, a random password, role `BRIDGE_DEFAULT_USER_ROLE`, unless provisioning is `disabled`, or `pre_approved` and not listed. An in-memory limit of 30 a minute per user follows (`:510-519`). `ai_chat` mode finds or makes a thread and a chat, rebuilds the history, makes one non-streamed completion with `bypass_filter=True` through the privacy door on a mock request, and answers through the adapter (`:73-216`). `channel_bridge` mode inserts a Space message tagged `data.bridge`, emits it to the room and, when the platform says the bot was mentioned, makes one more completion and posts it as the bridge user (`:218-384`).

**Bridges, outbound.** Every Space post not tagged `data.bridge` starts `forward_space_message_to_bridges` (`routers/spaces.py:626-637`; `bridges/outgoing.py:11-68`). For each enabled `channel_bridge` connection linked to that Space with a live adapter, it sends `*Name*: text` to every thread the connection knows. A 60 s health loop restarts sick adapters with a delay that doubles from 30 s to 300 s (`manager.py:215-250`).

**Voice.** Dictation: `VoiceRecording.svelte` records with `MediaRecorder` (or the browser's `SpeechRecognition` when no engine is set, `:215,266`), uploads to `POST /api/v1/audio/transcriptions`, which accepts `audio/*` or `video/webm`, saves the upload under the cache directory and calls `transcribe` (`audio.py:899`, `:1019-1090`); the text goes back to the composer. Read aloud: the SPA cuts the streamed answer into sentences (`C/chat/Chat.svelte:1248-1262`) and speaks each with `speechSynthesis`, the kokoro worker or `POST /api/v1/audio/speech`, which caches the mp3 under a hash of body, engine and model (`audio.py:316-330`). Call mode: `CallOverlay` records, watches the signal level for silence (`:288-340`), transcribes (`:157`), submits the text as a normal chat turn (`:170`) and speaks the reply. Grafting `whisper-base-ggml` repoints the `openai` STT engine at a loopback whisper server (`sprigs/stt_dispatch.py:20-44`).

**Images.** The composer toggle puts `features.image_generation` in the request (`C/chat/Chat.svelte:1706`). `process_chat_payload` then runs `chat_image_generation_handler` (`utils/middleware.py:934-1028`): it takes the last user message as the prompt, or a model-written prompt when `ENABLE_IMAGE_PROMPT_GENERATION` is on, calls `image_generations` (`routers/images.py:482`) in process, stores the bytes as `file` rows (`upload_image`, `:468`), emits a `files` event, and adds a system note so the chat model announces the image. The "generate image" button on a reply calls `/api/v1/images/generations` directly (`C/chat/Messages/ResponseMessage.svelte:438`). Each engine is one HTTP call (`images.py:499-700`); URLs the engine returns are fetched with a 60 s timeout (`:448-466`).

**Notes.** CRUD goes through `/api/v1/notes`; update and delete check `features.notes`, then owner, admin or the `write` list (`routers/notes.py:146-224`), and an update emits `note-events` to room `note:<id>` (`:172-178`). Live editing: `NoteEditor.svelte:769` emits `join-note`; `RichTextInput` with `collaboration` builds a Socket.IO provider (`RichTextInput.svelte:214-400`) and emits `ydoc:document:join` for `note:<id>`. The server checks `read`, registers the session in `YdocManager`, joins `doc_note:<id>`, replays stored updates into a `pycrdt.Doc`, sends the merged state to the joiner and `ydoc:user:joined` to the rest (`socket/main.py:389-463`). Each local edit sends `ydoc:document:update` with the update bytes and the editor's rendered `data`. The server appends the update to a per-document list in memory (Redis when configured), rebroadcasts it, and 0.5 s after the last edit saves the client's `data` into `note.data` (`:526-569`). Cursors travel as `ydoc:awareness:update` (`:605-622`). When the last session leaves, the in-memory document is dropped (`:572-602`; `socket/utils.py:166-198`). The CRDT state is never stored: the row holds whatever the last client rendered.

**Code.** A run button on a code block executes in a Pyodide worker and shows the result in the block; nothing returns to the model. Model-driven: with `features.code_interpreter` a prompt template is added (`utils/middleware.py:1267-1275`), the stream parser spots `<code_interpreter>` (`:1744,1902`), and after the round the server runs the code and feeds the output back, up to 5 times (`:2104-2200`). The `pyodide` engine sends `execute:python` to the user's live browser session with `sio.call` (`socket/main.py:713-726`; `routes/+layout.svelte:320-322`) and waits; `jupyter` posts to the configured server. Functions: `get_all_models` adds every active Pipe as a model (`utils/models.py:68`; `functions.py:56`), `generate_function_chat_completion` runs `Pipe.pipe(...)` (`utils/chat.py:275`; `functions.py:124`), Filters run as `inlet`, `stream` and `outlet` hooks (`utils/middleware.py:1243,1791`; `utils/chat.py:354`), and Actions are buttons that call `chat_action` (`utils/chat.py:363`). Loading a Function execs its stored source, rewrites the stored text when imports changed and pip-installs the frontmatter requirements (`utils/plugin.py:74-123,181-195`). Boot installs the requirements of every active Function (`main.py:636`).

**Arena and ratings.** `get_all_models` appends the Arena Model (`utils/models.py:118-145`). A chat to it reaches `_generate_chat_completion`, which picks a random non-arena model and recurses with `bypass_filter=True`; the stream's first line names the pick (`utils/chat.py:225-271`), and the message keeps `arena` and `selectedModelId`. A thumb click posts a rating with the model, its siblings and a snapshot of the chat to `POST /api/v1/evaluations/feedback` (`routers/evaluations.py:114-127`), and the message gets a `feedbackId`.

**LDAP.** The sign-in page posts `{user, password}` to `/api/v1/auths/ldap`. The server binds with the app DN, searches `(&(<username attribute>=<escaped user>)<filters>)` (`routers/auths.py:386-395`), re-binds as the DN it found with the typed password (`:477-485`), creates the user on first sight (`:487-512`), optionally syncs groups (`:415-475,548-575`) and sets the same `token` cookie as a password sign-in (`:520-550`). It never looks at `ENABLE_SIGNUP`.

**Vector databases.** `VECTOR_DB` picks one client at import (`retrieval/vector/factory.py:11-61`); a failed import leaves `VECTOR_DB_CLIENT` None and a 503 on use (`:56-69`). Boot runs the prefix migrations for all five (`main.py:652-654`).

**Ollama.** `get_all_models` merges the Ollama list into the OpenAI list. For a model owned by `ollama`, `_generate_chat_completion` converts the OpenAI payload to Ollama's shape, calls `/api/chat` and converts the stream back (`utils/chat.py:278-295`; `utils/payload.py:276-357`; `utils/response.py:82-130`). `/ollama/*` also serves other clients raw and skips the privacy filter (`AGENTS.md`). A connection's type defaults to `local` for Ollama and `external` for OpenAI (`routers/ollama.py:421`; `routers/openai.py:444`), and that decides whether the privacy filter applies (`privacy/hooks.py:48-56`).

## 3. Edge cases worth keeping

Tags in brackets name the feature. The shared harvest is `docs/rootstock/research/edge-cases.md`.

## 5. Rootstock equivalent

**What a Sprig contract names** (proposed, against the plan's `sprigs/` module, cap 520, and the Sprig spec). Five parts: the capability family and delivery; **wires**, the operator's settings, where a secret is never rendered back (`docs/orientation.md:203-208`); **routes** the core proxies to the Sprig (the plan's `expose: proxy`); **slots**, where its fragment mounts, with the DOM events it sends and takes; and **ops** its scoped key may call, with the events the core publishes to it. The board has decided the slot address as `page:position` (`home:top`) and built none of it: `SPRIG_ACTIVE_UI` is one pointer and one unnamed slot (board card "ui-Sprig NAMED SLOTS"; `pages/shell.py:108-151`). Every slot below is a new name for the registry to publish, versioned and never renamed in place.

Proposed slots: `chat:composer-tools` (buttons beside send), `chat:message-actions` (under a reply), `chat:code-actions` (on a code block), `chat:overlay` (a full-screen layer), `sidebar:nav` (a nav item), `space:header` (a status chip), `admin:page` (a settings page built from the Sprig's wire schema) and `page:<name>` (a whole page in a frame). Host events, DOM and bubbling: `composer:insert {text}` (the plan's one voice event), `composer:submit {text}` and `code:run {block, lang, code}`. The `ui-` script cap is 16 KiB (`sprigs/ui_dispatch.py:60`): room for a button and a small recorder, not for TipTap. An editor-sized Sprig has to be an `app-` frame, a family the spec reserves and a v1 rootstock refuses (`BONSAI/sprig-spec/v1.md:142`).

**Bridges** → family `bridge-<platform>`, a prefix to reserve, since the spec has none. Delivery: a loopback process for Telegram and email; WAHA and signal-cli need their own container, so `service-endpoint` or an operator sidecar. Wires: the platform credentials. Route: `POST /sprigs/bridge-<platform>/webhook/<connection>`, public, the Sprig checks the signature. Ops on its key: `bridge_user_resolve(platform, external_id, name)` (finds or makes a no-login account under the connection's provisioning rule), `message_post(space, content, data)` with the `data.bridge` tag, `ask(model, messages)` (the privacy door and a Receipt, `op=bridge_reply`), `bridge_thread_get` and `bridge_thread_put`. Events to the Sprig: `space.message {space, message, user, content}` for Spaces linked to its connections, never for tagged messages. Events from it: `bridge.status {connection, state, text}`. Slots: `admin:page` (connections and status), optionally `space:header`. Tables: `bridge_connection` and `bridge_thread` stay unmanaged models behind core ops; the Sprig never opens SQLite. The rate limit becomes a persisted per-user check inside `bridge_user_resolve`. Why a Sprig: 0 rows, heavy per-platform clients, credentials, and a ban risk on WhatsApp (Trellis `crm/docs/plans/loop.md:11`).

**Voice** → two families the spec already reserves, `whisper-` (STT, OpenAI `/v1/audio/transcriptions`) and `tts-` (OpenAI `/v1/audio/speech`), plus one `ui-` fragment for the buttons. The catalog calls its STT capability `stt` (`sprigs/supervisor.py:483`) where the spec reserves `whisper-`; align the name. Server half: a loopback OpenAI-shaped service (whisper.cpp ships, a TTS cultivar does not) and `media-ffmpeg` for browser webm. Core routes: `POST /sprigs/voice/transcriptions` and `/speech`, session-authenticated, with the `audio/*` and `video/webm` allowlist and a size cap. External engines (OpenAI, Deepgram, Azure, ElevenLabs) become `service-endpoint` Sprigs or audio connections; either way a call opens a Receipt (`op=transcribe` or `speak`, sizes only) and TTS text passes the privacy policy. Slots: `chat:composer-tools` (mic; sends `composer:insert {text}`), `chat:message-actions` (read aloud; reads the text from the message element), `chat:overlay` (call mode; sends `composer:submit {text}` and listens for `chat:sentence {id, text}`, which `message.lastSentence` supplies by accident today), `admin:page` (the 23 settings become an engine choice and its few fields). Personal choices stay user settings; 5 users hold them. Risk: call mode is 955 Svelte lines, and the 16 KiB script cap leaves it little room unless it is rewritten small or the cap rises for signed Sprigs.

**Images** → family `imagegen-` (reserved; OpenAI `/v1/images/generations`). ComfyUI and Automatic1111 are external servers, so `service-endpoint`; OpenAI and Gemini are external APIs, so connections of an `images` kind. The core op is `image_generate(prompt, size, n)`: it applies the privacy policy to the prompt, opens a Receipt (`op=image`), calls the Sprig or connection, stores the bytes as `file` rows and returns file ids. The chat turn calls it first when the composer toggle is on, which is today's pre-step (`utils/middleware.py:934-1028`), and the "generate image" action calls the same op. Slots: `chat:composer-tools` (toggle; event `composer:feature {name: "image", on}`), `chat:message-actions` and `admin:page` (19 settings become one engine and its few fields). No table of its own. Why a Sprig: the engines are external services, the feature is optional, and the census cannot say how often it runs.

**Notes** → family `app-`. The editor is a self-contained application: TipTap and Yjs are 33 packages, far past the `ui-` cap. It runs in the Workshop apps frame (`/apps/<id>/<sha>/`, sandboxed, never `allow-same-origin`) with a service half: an `oci-artifact` process (`pycrdt` and a WebSocket server) and `expose: proxy` routes `GET /sprigs/notes/*` (the editor files) and `WS /sprigs/notes/sync/<note>` (Yjs). Ops on its key: `note_can(user, note, verb)` (the `access_control` rule, with `write` for updates), `note_get`, `note_save(note, text, files)` and `note_list(user)`. The Sprig applies updates to a server-side `pycrdt.Doc`, keeps the CRDT state in its own file, and saves the merged text through `note_save` after a quiet period; that fixes edge cases 14 to 16. Slots: `sidebar:nav` (Notes) and `page:notes`. Table: `note` stays an unmanaged model (17 rows). The app reaches chat and voice through the bridge's `ask` (privacy door, Receipt) and the voice Sprig's mic event.

Open point: the plan's app CSP is `connect-src 'none'` and a sandboxed frame carries no session cookie. Live sync needs either a host relay (a bridge `sync` method that passes Yjs updates, under the 256 kB message limit) or a narrower CSP, `connect-src 'self'` plus a short-lived token from a bridge call, for signed first-party apps. Decide with the apps host in F5. Until the Sprig ships, the legacy routes keep answering and the 17 rows stay readable only through the old app. A box keeps its notes in the meantime by the database download, which holds every row; `GET /api/v1/notes/` returns only the caller's own and writable notes (`routers/notes.py:49`).

**Code execution** → three contracts, in this order of need.

- **Model-driven runs** → a tool-server Sprig, `code-run`: OpenAPI at loopback, `POST /run {language, code, timeout}` returns `{stdout, stderr, result, files}`. The chat tool round (cap 10) calls it like any tool server, so the `<code_interpreter>` tags, the run loop and about 140 middleware lines go. It wraps Jupyter, today's second engine, or runs Pyodide in a server-side runtime, so it needs no open browser tab (edge case 20). Wires: engine, Jupyter URL and token, timeout.
- **The run button** → the `code-pyodide` static Sprig (it exists) and a `ui-` island on `chat:code-actions`. Event `code:run {block, lang, code}`; the island runs the worker and writes the result under the block. Nothing returns to the model.
- **Functions** → a `plugin-` host Sprig, built only where a box census shows use (the snapshots hold 1 inactive Pipe). It loads the stored source in its own process with a trimmed environment (no `WEBUI_SECRET_KEY`), serves Pipes as an OpenAI-shaped `/v1/chat/completions` so a Pipe is a connection with models, and Filters through two core hook points, `inlet` and `outlet`, that `chat_turn` calls only while a plugin Sprig is grafted. Actions are `chat:message-actions` buttons, valves are wires, and requirements install at graft time, never in the running core. The `function` table stays an unmanaged model behind ops. Pipelines servers are plain OpenAI connections; their filter calls (`process_pipeline_inlet_filter`) are not carried.

**The four cuts: what each leaves behind, and how a box keeps it.** The Rootstock never alters legacy tables (plan, cutover rules), so a cut feature's rows stay in the file and in every database download. They are unread, not gone.

- **Arena evaluations.** Leaves `feedback` (30 rows, 32 in the backup) and per-message keys in the chat JSON: `feedbackId` on 29 messages, `annotation` on 31, `arena` and `selectedModelId` on 4. The chat reader ignores unknown keys. A box keeps the ratings by taking the JSON export before the router goes (`GET /api/v1/evaluations/feedbacks/all/export`, `routers/evaluations.py:96`). The thumbs are the open question (edge case 23): if kept, a `message_rate` op writes the same table in the same shape. The Arena Model leaves every picker.
- **LDAP.** Leaves nothing in the file: no `ldap.*` key is saved in either database and no user has an `oauth_sub`. A box that uses it puts the directory behind an OIDC provider. AI-UI is already an OIDC client (`oauth.oidc.*`, `config.py:410-430`) and merges a sign-in into an existing account by email (`OAUTH_MERGE_ACCOUNTS_BY_EMAIL`, default True, `config.py:304-308`; `main.py:2176`), so accounts LDAP created keep their chats. Groups LDAP created are ordinary `group` rows. Check each box's `ldap.enable` with the census verb before F2.
- **Five vector databases.** Leaves vectors in the external service, unreadable to the Rootstock, plus `file.meta.collection_name` on 392 of 2,193 files and `knowledge.data.file_ids` on 13 of 18 knowledge rows. A box keeps its knowledge by re-indexing into SQLite from `file.data.content` (1,080 files) and re-extracting the other 1,113 from their stored `path`. Search refuses until that has run (plan). Chroma users opt in to the vector-chroma Sprig per knowledge base. The operator deletes the external collections afterwards.
- **The Ollama proxy.** Leaves `ollama.*` (one URL, disabled) and `model` rows whose `base_model_id` names Ollama ids. A one-time conversion writes an `openai`-kind connection at `<ollama url>/v1` with `connection_type: local` and the old `prefix_id` from `ollama.api_configs`, so those ids still resolve (`routers/ollama.py:421-443`; `routers/openai.py:444-458`; read, not run). The `ollama` embedding engine converts to `openai` at `/v1/embeddings`. Pulls move to the Ollama CLI. Raw `/ollama/*` clients lose the route: list them per box before F7.

**Order inside F7, by dependency.** The cuts that need a conversion script come first (Ollama connections, the LDAP check). Bridges, voice, images and code need the slot registry, scoped keys, `expose: proxy` and the Receipt ops, so they follow F3 and F5. Notes comes last, since it needs the apps host and the CSP decision above. The plan's admin table lists `evaluations` as Sprig-provided while the cut list drops it (plan lines 31, 218, 272); settle one.
